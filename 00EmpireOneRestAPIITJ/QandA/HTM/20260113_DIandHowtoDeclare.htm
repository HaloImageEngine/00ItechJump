What are the 3 ways to declare a DI and where do they exist?

There are three common ways to declare (register) Dependency Injection (DI) services, and they primarily exist in the application startup / composition root (where the app is configured), not scattered throughout business logic.

1. Transient

Where it exists:
Registered in the DI container configuration (e.g., Program.cs or Startup.cs in ASP.NET Core)

How it’s declared:

services.AddTransient<IEmailService, EmailService>();

What it means:
A new instance is created every time the service is requested.

Typical use cases:

  • Stateless services
  • Lightweight helpers
  • Short-lived operations

2. Scoped

Where it exists:
Registered in the DI container configuration, with the lifetime managed per request scope (usually an HTTP request)

How it’s declared:

services.AddScoped<IOrderService, OrderService>();

What it means:
One instance is created per request, shared across that request.

Typical use cases:

  • Database contexts (DbContext)
  • Request-specific business logic
  • Unit-of-work patterns

3. Singleton

Where it exists:
Registered in the DI container configuration, with the instance living for the entire application lifetime

How it’s declared:

services.AddSingleton<ICacheService, CacheService>();

What it means:
A single instance is shared by all users and all requests.

Typical use cases:

  • Caching services
  • Configuration providers
  • Logging services

Where DI Is Used (Not Declared)

Although DI is declared in startup, it is consumed in:

  • Controllers
  • Services
  • Background workers

 

}

Summary

  • Declared in: Program.cs / Startup.cs (composition root)
  • Three lifetimes: Transient, Scoped, Singleton
  • Used via: Constructor injection throughout the application
